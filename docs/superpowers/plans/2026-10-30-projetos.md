# Entrega 2: Projetos (sala = projeto) — Plano

Spec: docs/superpowers/specs/2026-10-30-habblaud-hermes-design.md (Modelo de dados, Funcionalidades 2).

Objetivo: a sala deixa de ser uma pasta e passa a ser um projeto com zero ou mais pastas. Pasta fora de qualquer
projeto continua virando sala sozinha (comportamento atual).

Formato de `<dataDir>/projects.json`:

    { "projects": [ { "id": "p_<aleatório>", "name": "...", "paths": ["/a", "/b"], "context": "..." } ] }

Regras:
- Uma pasta pertence a no máximo um projeto. O cwd do agente casa com o projeto da pasta mais longa que é prefixo
  dele (`/a/b/c` casa com `/a/b`).
- A sala de um projeto tem id `project:<id>`; a de pasta solta continua com o cwd normalizado.
- O agente passa a ter o próprio `cwd` (hoje o terminal usa o caminho da sala, o que deixa de valer).
- O contexto fixo do projeto é guardado agora e usado na entrega 3 (fichas).

## Tarefa 1: ProjectStore
`server/projects/store.ts` + teste. Carrega/salva (escrita atômica, chmod 600), list, create, update, remove,
addPaths, match(cwd). Valida nome (1..40), pastas absolutas, sem pasta repetida entre projetos.

## Tarefa 2: Office usa projetos
`AgentInfo.cwd`; roomId vindo de `match`; `RoomInfo.paths` e `RoomInfo.project`. Ao mudar projetos, os agentes
vivos são recalculados e mudam de sala. Terminal usa `agent.cwd`. Renomear sala de projeto renomeia o projeto.

## Tarefa 3: Rotas
GET/POST `/api/projects`, PATCH/DELETE `/api/projects/:id`. "Transformar em projeto" = POST com as pastas da sala;
"Juntar com…" = PATCH acrescentando as pastas da outra sala. Remoto: feature `projects`.

## Tarefa 4: Interface
Menu da sala: Transformar em projeto, Juntar com…, Editar projeto (nome, pastas, contexto), Desfazer projeto.
i18n en/es/fr.

## Tarefa 5: Build, deploy no container e verificação

Fica para a entrega 3: promover consulta (precisa da ficha de agente).
